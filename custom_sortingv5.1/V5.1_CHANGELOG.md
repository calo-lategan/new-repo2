# custom_sortingv5.1 — Changelog

`custom_sortingv5.1/` is the finalised JetArm sorting app — a copy of
`custom_sortingv5/` with the fixes below. **It installs SIDE-BY-SIDE with v5,
not over it.** Running `custom_sortingv5.1/install.sh` deploys under distinct ROS
entry points (`custom_sortingv51` / `tune_uiv51`, symlinked as
`custom_sortingv51.py` etc.), its own launcher dir (`~/jetarm_v5_1/`), and a
separate **"JetArm Sort v5.1"** desktop icon — so v5's icon and deployment are
left fully intact as a one-click fallback. (The source filenames stay
`custom_sortingv5.py` etc.; only the *installed* link/entry names differ.)
`install.sh`'s `V4` dir was also fixed to `custom_sortingv5.1/` (it pointed at
`custom_sortingv5/`, so v5.1 would never have deployed). Shared, version-agnostic
dirs (`~/jetarm_v5_profiles/`, `~/jetarm_v5/logs/`) are reused. Only one stack
runs at a time (a single arm).

> ⚠️ **Not verified on hardware.** Every change here is from static analysis +
> comparison against the vendor source (`full jetarm source for context src/`).
> The author had no ROS / arm / camera / engine access. Run
> `ON_ARM_TEST_CHECKLIST.md` on the JetArm to verify. Items touching the
> world-position math (B1) and chassis path (C1) are the ones most likely to
> need on-arm confirmation.

Each fix is tagged in code with a `v5.1 FIX (<id>)` comment so you can grep it.

## NEW FEATURE — Bin Teach & Workspace Map (tuner UI → "Bin Teach" tab)

Fixes "everything places in the wrong spot (~12 cm off, in front instead of at
the side bins)". The default `place_positions` were the vendor forward-grid demo
zones, not the operator's real bins. Rather than measuring coordinates by hand,
you now **jog the arm to each physical bin, read its live world coordinate, and
save it** — and the cube then drops exactly there.

**A saved bin is just a drop LOCATION, not an arm pose.** The place pipeline
(`_do_place`) still computes its own approach (hover above → descend → release);
teaching only sets where. The key correctness point: a hand-taught bin is a real,
physically-reached arm-base coordinate, so `_do_place` drives **straight to it and
skips the kinematics scale/offset affine** (that affine is a *vision-reach*
correction for camera-derived picks; re-applying it to a taught bin would shift
the drop ~5 % + a few mm off). Taught bins are tagged `[x, y, z, "taught"]` in
`place_positions`; legacy/Places-tab entries stay 3-element and keep the affine.

What the tab does (all via a new `~/teach` `SetStringBool` service; refused while
sorting/calibrating):

- **Joint jog** (servos 1–5, ± by a pulse step) — moves the arm *joint by joint*,
  never needs IK, so you can reach bins even at the edge of the workspace. Reads
  all five servos in one bulk call, commands one, then reports the resulting world
  coordinate via **forward kinematics** (verified: the FK service and the IK/place
  frame are one and the same arm-base frame).
- **World jog** (X/Y/Z ± via IK) for fine straight-line nudging.
- **Live readout** of world `(x, y, z)` + servo pulses, pushed on a dedicated
  low-latency `~/teach_status` topic (the 5 s heartbeat is too slow to jog with).
- **Save here → <class>** stores the readout as that class's bin (optionally
  persisted to `default.yaml`); **Go to bin** drives there to verify.
- **Saved bins list** — one row per class with its live coordinate (taught / set
  / default) and a **Go** button: jump straight to an already-set bin, nudge with
  the jog buttons, and re-save, instead of hand-jogging from scratch. The list
  stays live via `place_positions` carried on `~/teach_status`.
- **Workspace map** — teach the mat **centre** and **edges** to re-anchor the
  world origin: it rewrites **only** `white_area_pose_world`'s translation in
  `transform.yaml` and sizes the overlay via `workspace_size_x/y`. It **never**
  touches the AprilTag camera geometry (`extristric` / `corners` / `plane`), which
  can't be recovered from arm poses — so **run AprilTag CALIBRATE first**; this is
  a supplement, not a replacement. A guardrail refuses a centre > 5 cm from the
  current origin unless you tick **Confirm** (catches mis-jogs).

Note: editing a taught bin on the **Places** tab and saving rewrites it as a
3-element manual entry (the affine re-applies). Use Bin Teach for exact placement.

**Hardware round 1 fixes** (on-arm: joint jog + Go did nothing):
- **Joint jog "cannot read servo positions"** even with `bus_servo/get_state`
  up: the one-shot *bulk* 5-servo request returned < 5 states on this driver
  build, so the read was dropped. Now reads servos 1–5 with the proven
  single-servo `get_servo_state` path (5 serial reads), with a longer 1.5 s
  per-read timeout (the standard grasp never exercises servo reads, so the
  first reads can be slow).
- **World Go / Home "UNREACHABLE (IK)"** while real picks/places succeed:
  teach moves used the `(-90,90)` *grab* pitch range; switched to the default
  `(-180,180)` that `_do_place` uses, and **Go** now mirrors `_do_place`
  (hover-above → descend) so it reaches exactly what placement reaches.
  **Home** now commands the physical home servo config directly (IK to a fixed
  `[0,0.2,0.1]` had no solution at pitch 80). The world-jog seed now comes from
  the arm's actual FK pose, not a hardcoded guess.

**Hardware round 2 fixes** (servos still didn't move):
- **This arm can't report servo positions.** `bus_servo/get_state` advertises
  but every read (bulk *and* serial) returns no data — the standard grasp is
  open-loop too, which is why it otherwise works. Joint jog was bailing on the
  failed read *before* commanding the servo, so nothing moved. Joint jog is now
  **open-loop**: it TRACKS the commanded joint pulses (seeded by **Home**, or a
  successful world goto/jog) and jogs relative to them; the live world readout
  is FK of the tracked pulses (FK works — it's how the init endpoint is
  captured). Press **Home** first to sync, then jog — servos now move.
- The `read` action and world-jog seed no longer depend on servo reads either.
- ⚠️ Watch the boot log: the session where jog/IK failed ran with
  `CHASSIS_TYPE='None'` (→ `config_path=app/config`), whereas the session where
  picks/places worked ran `CHASSIS_TYPE='Slide_Rails'` (→ `stepper/config`).
  Launch v5.1 with the Hiwonder env sourced so `CHASSIS_TYPE=Slide_Rails`, or
  IK/calibration use the wrong config and bins won't line up.

## CRITICAL

### A1 — Color calibration was driving the wrong node name
`tune_uiv5.py` calls `/lab_manager/*` and subscribes to
`/lab_manager/image_result`, but the vendor LAB node names itself
`lab_config_manager` (`lab_manager.py: LabConfigManagerNode('lab_config_manager')`)
and the launch included the vendor launch with **no `name=` remap**, so the
real services were `/lab_config_manager/*`. Every Color-tab call (enter / get /
change / stash / save) timed out and the mask preview never rendered.
**Fix:** `custom_sorting_nodev5.launch.py` now starts the node directly with
`name='lab_manager'`, so the runtime services/topics match the UI and docs.
`lab_config.yaml` uses the `/**` param wildcard, so the rename doesn't affect
parameter loading.

### B1 — World-position depth path ran with an identity endpoint pose
The vendor `utils.calculate_world_position` computes the pick point as
`(endpoint + pose_end)[:3,3]` — it **adds** the arm-base→hand translation
(`endpoint`). v5 read `getattr(self.motion, 'last_endpoint_pose', None)`, which
was **never set anywhere**, so it always fell back to identity → the arm-base
offset was dropped and every depth-path pick was computed as if the camera were
at the world origin (lands off to the side).
**Fix:** new `_capture_endpoint_pose()` calls the kinematics FK service
(`kinematics/set_joint_value_target`, already wired) for the fixed observe
config `[500,520,210,50,500]` and stores the real endpoint pose, exactly as the
vendor `shape_recognition.go_home` does. Captured once on a dedicated startup
thread (cached; never on the executor thread). Falls back to the legacy
calibrated path with a clear log if FK is unavailable.

## HIGH

### A2 — A `no_feedback` grasp could place an empty gripper
With compliance grasp on, if the gripper servo readback failed the code did one
blind close, returned `no_feedback`, and **kept the optimistic lift** → placed a
possibly-empty gripper. **Fix:** `no_feedback` now fails the pick by default
(new `grasp_fail_on_no_feedback`, default `true`); transport then re-opens and
re-locks. Set the param `false` only if this arm's gripper servo genuinely never
reports position.

### A3 — Depth median gate dropped edge detections
The window-validity threshold divided by the **full** `(2*half+1)²` even though
the patch is image-clamped near edges, so any detection within `depth_window_px`
of a border was rejected even with perfect depth. **Fix:** gate against the
actual clamped patch size. Applied in both `_depth_at` and the vendor-path
re-sample in `get_object_world_position`.

### B3 — Depth-topic selection committed before confirming publication
`create_subscription` never fails for a non-publishing topic, so the old loop
always locked onto `/depth_cam/depth_to_color` and `break`ed — if only the raw
topic published, depth stayed dead with no fallback. **Fix:** subscribe to both
candidates; whichever **delivers frames** wins (`_depth_callback` selects),
upgrading to the colour-aligned `depth_to_color` stream if it appears.

## MEDIUM

### A4 — No safe transit pose between pick and place (collision risk)
v5 lifted only `hover_height` (~6 cm) above the pick point, then `_do_place`
traversed horizontally at that low height. The vendor `pick()` retreats to a
fixed safe pose `[0.11,0,0.09]` with the wrist centred first. **Fix:** after a
successful grab, retreat to the vendor transit pose before the place traverse
(new `safe_transit_enabled`, default `true`). Best-effort: a transit IK miss
logs and continues — it must not drop the held object.

### A5 — Position-calibration finish timeout too short
The wait on `/calibration/finish` was 20 s, marginal vs the vendor success path
(arm settle + ~10 s tag collection + solvePnP + a synchronous
`get_current_pose` + RANSAC). A short timeout called exit and aborted a
calibration that would have succeeded. **Fix:** raised to 35 s.

### B4 — OBB grasp-axis convention + a hardware yaw knob
Confirmed via the ultralytics OBB docs (Context7): `r` is radians normalized to
`[-45°,135°)`, `w` is the **long** side, and `r` is the angle of `w`. v5's
short-axis-clamp logic is therefore correct in software (it clamps the narrow
waist — what the scaff needs). The only real risk is a physical gripper-mounting
offset. **Fix:** corrected the misleading `r ∈ [-π/2,π/2]` comment and added
`grasp_yaw_offset_deg` (default 0, range ±180) added to the OBB angle, so a
90°/180° mounting offset is corrected from a profile/preset instead of editing
code.

### C1 — Calibration config path ignored chassis type
The vendor `calibration_node` writes `transform.yaml` to `stepper/config` when
`CHASSIS_TYPE=Slide_Rails` but `app/config` otherwise. v5 hardcoded `app/config`,
so a fresh Position/Depth calibration could be written to one file while v5 read
a stale other one. **Fix:** branch `config_path` on the same `CHASSIS_TYPE` env
var the vendor uses. **Resolved with the operator:** this JetArm **is** a
Slide_Rails arm — `Slide_Rails` is its lead-screw rail axis, not a mobile
chassis, and the vendor kinematics (`driver/kinematics/transform.py`), pick
(`pick_and_place.py`) and calibration all branch on it. So
`CHASSIS_TYPE=Slide_Rails` is **left as-is** (changing it would break the IK) and
v5.1 correctly reads `…/stepper/config/transform.yaml`. No launcher change.

## LOW / housekeeping

- **A6a** — `set_value` now returns whether the node accepted the param. Speed
  presets no longer push keys live; they route through `load_profile` (see
  Presets), which applies one param at a time and can't silently drop a key.
- **A6b** — `call_enable_sorting` waits 5 s for the service (was 1 s; matches
  every other client) so START doesn't spuriously report the node unreachable.
- **A6c** — `_selected_engine_path` ignores the `(dir not found…)` / `(no
  .engine…)` listbox placeholders instead of building a bogus engine path.
- **A6d** — `_refresh_class_filter` no longer makes a **blocking** `get_values`
  call on the Tk poll thread (it could freeze the UI ~2 s when class names
  changed). The persisted enabled-class list is fetched once on a worker thread
  and cached; the rebuild uses the cache (all classes on until it's warm).
- **A7** — removed a duplicate `last_calibrate` key in the heartbeat dict (it
  could throw and blank the whole UI status); corrected the stale
  "merges yolo.yaml" comment in `default.yaml` and the stale "falls back to
  inline solvePnP" calibration dialog text.
- **Deploy (install.sh)** — `V4` (the app dir the installer symlinks from and
  seeds profiles from) now points at `custom_sortingv5.1/` instead of
  `custom_sortingv5/`. As copied, v5.1's installer would have deployed **v5's**
  code; this makes v5.1 actually install itself.
- **Thread-safety** — added a `threading.Lock` (`_transport_lock`) around the
  `start_transport` / `transport_info` / `target` handoff between the detection
  (`sorting_loop`) and motion (`transport_thread`) threads and the enable/exit
  callbacks (the vendor uses an RLock here; v5 had none). Held only for the
  brief field assignments — never across motion/IO — so it cannot deadlock; the
  long pick/place runs outside it. `transport_thread` also snapshots + copies
  the position so the in-place `+= 0.01` can't alias the detection thread's list.

## Performance & comment cleanup (P1–P3)

- **P1** — `_raw_republish_tick` (the 30 Hz overlay compositor) now **bails when
  no one is subscribed** to the raw or compressed result topic. It was running
  the overlay composite + `cv_bridge` + DDS publish every frame even with no
  viewer (the JPEG sibling was already gated in `_publish_image`).
- **P2** — comment cleanups: `_detections_from_results` docstring no longer says
  "YOLO + LAB color blobs" (v5 is YOLO-only); the stale HED references (the
  "~0.4 fps depending on HED" rate in `_raw_republish_tick` and `_draw_overlay`,
  and the "HED-on iteration" overlay-age comment) are gone — v5 has no HED path.
  (The two comments that *state HED is absent* are accurate and were kept.)
- **P3** — removed a dead per-frame compute in `_depth_callback`: it ran
  `vendor_utils.get_plane_values(full_frame, plane, K)` on every depth frame and
  stored it in `self._plane_values`, which **nothing ever read** — a full-frame
  vectorised pass whose result was discarded.

## Presets — Slow / Medium / Fast

The "Presets" bar has exactly three presets — **Slow / Medium / Fast** (Medium
== `default.yaml`). They ship as **partial profile YAMLs**
(`profiles/{slow,medium,fast}.yaml`), and each button **loads its file through
the node's existing `load_profile` service** on a worker thread (`SPEED_PRESETS`
+ `_on_load_speed_preset` in `tune_uiv5.py`). This reuses the node's hardened
one-param-at-a-time apply (type/range tolerant), so it can't silently drop a key
the way the old live per-key `_apply_preset` push could. Each file adjusts only
the speed↔accuracy knobs below; engine, calibration, depth and place-zone
settings are intentionally **not** touched. `install.sh` seeds the three files
next to `default.yaml`; `fast`/`medium`/`slow` are reserved slugs and hidden
from the custom-preset combo. All values are inside each tunable's declared
range.
